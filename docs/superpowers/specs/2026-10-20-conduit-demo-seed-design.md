# Conduit 演示数据种子设计

- 日期：2026-10-20
- 状态：已实现
- 目标：新电脑或全新数据库完成迁移后，立即得到与开发环境一致的演示资产；启动模拟器后全部演示设备持续产生合理遥测。

## 1. 数据边界

Flyway `V4__demo_seed.sql` 固化关系库中的稳定基线：4 个租户、8 个产品、174 台设备和 36 个物模型属性。数据名称、数量与现有开发环境一致，产品 Key 固定，新增设备 Key 使用可读且稳定的前缀。

不把在线状态、最新值和历史曲线写进迁移：它们分别属于 Redis 与 InfluxDB，会随时间过期，也不应伪造成数据库初始化时间附近的实时数据。模拟器负责在启动后重置演示设备密钥，并按物模型、日曲线和可靠上报协议持续生成这些动态数据。

## 2. 升级与安全

- 租户按 code、产品按同租户内名称、设备按同产品内名称复用；已有部署升级不会重复插入当前演示资产。
- 物模型按产品与 identifier 使用唯一约束补齐，不覆盖用户已有定义。
- 种子设备只存没有公开对应明文的占位哈希，不能直接接入；模拟器通过受保护 API 重置密钥后才连接 MQTT。
- 不在迁移中写平台或租户账号密码。默认租户管理员和平台管理员仍由 `AdminBootstrap` 使用部署环境变量创建。

## 3. 模拟器

独立部署中的 `SIM_PLATFORM_PASSWORD` 默认复用 `CONDUIT_PLATFORM_ADMIN_PASSWORD`，因此默认租户的演示电表及另外三个演示租户的全部物模型产品都会被发现和模拟。可通过 `SIM_TENANTS` 缩小范围，通过 `SIM_MAX_DEVICES_PER_PRODUCT` 限制每产品设备数。

## 4. 验收

1. 全新 schema 迁移后恰好有 4 个租户、8 个产品、174 台设备、36 个物模型属性。
2. 从 V3 且已有默认演示产品/设备的 schema 升级，不重复产品和同名设备。
3. 全量后端测试、e2e 和前端测试通过，并产出测试报告。

## 5. 已知取舍（2026-10-20 复核）

曾讨论把播种从 Flyway 迁移移到受配置控制的启动组件，使演示数据可开关。结论是**维持现状**：`V4__demo_seed.sql` 不改动。

因此需要知道这个取舍的后果：**任何执行迁移的环境都会得到这批演示数据**，包括将来的真实部署；迁移一旦执行就不能再改（校验和会对不上），所以日后若要去掉，只能另写一个删除迁移，V4 本身仍留在历史里。

维持现状的理由是改动需要修改已执行过 V4 的两个数据库（开发库与演示 VM），而当前用途是个人研究与演示，演示数据出现在每个环境正是想要的效果。真要部署成不含演示数据的环境时再重新评估。
