# Conduit V0.2-R3 设计：遥测重放

- 日期：2026-10-20
- 状态：已评审，待实现
- 范围：平台管理员按时间范围把 Redis 总线中的原始报文重新写入时序库，用于 InfluxDB 断电丢数后的恢复；接口 + 前端入口。
- 前置：V0.2-R2 端到端可靠上报已完成。

## 1. 背景

`docs/durability-validation.md` 与 2026-10-20 的 InfluxDB 专项调查查明：InfluxDB 3 Core 3.12.0 的写入响应不代表数据已落盘。

核对 v3.12.0 源码：`no_sync` 默认为 `false`（`influxdb3_types/src/http.rs`、`influxdb3_server/src/http.rs`），走 `WalObjectStore::write_ops`（`influxdb3_wal/src/object_store.rs`）等待 `object_store.put_opts` 返回；但 `object_store` 0.12.5 的 `LocalFileSystem::put_opts`（`src/local.rs`）只做 `write_all` 加 `rename`，**没有 `sync_all`**。所以 2xx 的含义是「字节已进入操作系统页缓存、文件已改名」。

实测：默认设置下强杀进程三轮均 2000/2000 幸存；`no_sync=true` 时 2000 条只剩 1380。因此默认值必须保持不变，不能为了吞吐改用 `no_sync=true`。真正的丢数据窗口是内核回写窗口（Linux 默认约 30 秒），不是 WAL 的 1 秒刷新间隔。

这个缺口无法在 Conduit 侧消除：缺的 fsync 在 `object_store` 内部。但**数据并没有真正丢失**——`XACK` 只把消息移出待确认列表，条目本身仍留在 Redis 流中直到被 `MAXLEN` 裁剪（默认 100 万条，按当前约每秒 17 条计约 16 小时），而 Redis 配置为 `appendfsync always`。所以恢复手段是把流中的原始报文重新灌一遍。

## 2. 目标

- 平台管理员可以按时间范围重放，恢复 InfluxDB 丢失的时序数据。
- 重放可取消，可查看进度与结果。
- 重放不污染在线状态与死信统计。

不包含：自动检测丢数并触发重放、跨实例的任务状态、历史任务列表、重放租户级数据隔离（重放本就是跨租户的平台操作）。

## 3. 为什么重放是安全的

| 写入目标 | 重放旧数据的影响 |
|---|---|
| InfluxDB | 同 `tenant_id`/`product_key`/`device_key`/时间戳覆盖为相同值，无副作用 |
| 最新值 | `latest-update.lua` 逐测点比较时间戳，旧值不覆盖新值；`__last` 仅在更大时前移 |
| 在线状态 | **会把已离线设备标成在线，必须跳过**（见 4.3） |
| 死信 | **会重复写入，污染首页「最近 1 小时死信」，必须跳过**（见 4.3） |

因为前两项幂等，重放不需要先检测丢了哪些数据：非正常重启后直接重放最近一段即可，重复重放无害。

## 4. 服务端

### 4.1 接口

| 方法与路径 | 说明 |
|---|---|
| `POST /api/v1/platform/telemetry/replay` | 提交重放。体 `{"from": <毫秒>, "to": <毫秒>}`，返回当前任务状态 |
| `GET /api/v1/platform/telemetry/replay` | 查询当前任务状态；从未提交过返回 `{"state": "NONE"}` |
| `DELETE /api/v1/platform/telemetry/replay` | 请求取消正在运行的任务；没有运行中的任务返回 409 |

路径位于 `/api/v1/platform/**`，`SecurityConfig` 既有规则已限定只有平台管理员可访问，无需新增权限判断。

**参数校验**：`from` < `to`，二者均在 0～253402300799999 内，跨度不超过 **6 小时**，否则 400。跨度上限用于防止把 `from` 误写为 0 而重灌整条流。

**并发**：同一时刻只允许一个任务。已有任务运行中时 `POST` 返回 409。因此查询与取消都不带任务 id。

### 4.2 任务状态

状态保存在内存（单个 `AtomicReference`），不持久化：server 重启时重放本身已经中断，持久化状态只能用于事后查看，价值不足以引入额外存储。最近一次完成的任务状态保留到下一次提交为止。

```json
{
  "state": "RUNNING | SUCCEEDED | FAILED | CANCELLED | NONE",
  "from": 1760400000000,
  "to": 1760403600000,
  "startedAt": 1760404000000,
  "finishedAt": null,
  "scanned": 51234,
  "written": 51000,
  "skipped": 120,
  "rejected": 114,
  "error": null
}
```

| 字段 | 含义 |
|---|---|
| `scanned` | 从流中读出的条目数 |
| `written` | 成功写入时序库的测点消息数 |
| `skipped` | 解码失败、产品已删除、非属性消息等跳过的条数 |
| `rejected` | 物模型校验剔除了全部测点的条数（不写死信，仅计数） |

### 4.3 执行

1. 用 `XRANGE <上行流> <from>-0 <to>-0` 按批（每批 500 条）读取。Redis 流的条目 ID 前半段即毫秒时间戳，时间范围直接对应 ID 范围，无需额外索引。区间左闭右开（`to` 当毫秒本身不含在内），与设备列表的时间筛选约定一致。
2. 每批走现有流水线的处理路径：解码 → 物模型校验 → 写 InfluxDB → 写最新值。
3. **跳过在线状态更新**：重放的是旧数据，其接收时间会把已离线设备标成在线。
4. **跳过死信写入**：仅计数。原始那次处理若已进死信，记录已经在流里了。
5. 每批之间检查取消标志；已取消则停止并把状态置为 `CANCELLED`，保留已完成部分的统计。
6. 可恢复错误（InfluxDB 不可达等）沿用流水线既有的退避重试；连续失败超过重试上限则任务置为 `FAILED` 并记录原因。

重放与正常流水线并行运行，两者写同一个时序库。因为写入幂等，不需要互斥。

实现上把「解码 → 校验 → 写库 → 写最新值」这段从 `PipelineProcessor` 中提取为可复用单元，由正常消费与重放共用，两者的差别只在是否更新在线状态、是否写死信。

## 5. 前端

新增页面「数据重放」，归入平台管理员的「系统管理」菜单组。

在 `router/meta.ts` 的 `ROUTE_META` 中登记：

```ts
'telemetry-replay': {
  title: '数据重放',
  menu: '/telemetry-replay',
  scope: 'platform',
  breadcrumb: [{ label: '系统管理' }, { label: '数据重放' }],
}
```

页面构成：

- `PageHeader`，副标题说明用途与边界：重放把总线中保留的原始报文重新写入时序库，用于断电后恢复；同设备同时间戳覆盖为相同值；不更新在线状态，不重复写死信。
- 时间范围选择：`el-date-picker` 的 `datetimerange`，必填，跨度超过 6 小时时前端先行提示，不依赖服务端报错。
- 「开始重放」按钮，提交前弹确认，列出所选范围。
- 当前任务卡片：状态标签、起止时间、四项统计、耗时；运行中显示「取消」按钮（带确认）。
- 运行中每 2 秒轮询一次状态，任务结束即停止轮询。离开页面时清除定时器。
- 从未提交过任务时显示 `el-empty` 加引导文案。

文案与样式遵循既有约定：中文、`PageHeader`、只用 CSS 变量、深色主题下可读。

## 6. 测试

### 6.1 服务端

- 参数校验：`from >= to`、超出取值范围、跨度超过 6 小时均返回 400。
- 并发：任务运行中再次提交返回 409。
- 权限：租户管理员与只读用户访问三个接口均被拒。
- 集成测试（Testcontainers）：向流中写入若干条已知报文，清空 InfluxDB 对应时间段，执行重放，断言时序库中条数与内容恢复、统计字段正确。
- 在线状态：重放前把某设备置为离线，重放后断言仍为离线。
- 死信：重放一条物模型校验不通过的报文，断言死信流长度不变且 `rejected` 计数加一。
- 取消：提交较大范围后立即取消，断言状态为 `CANCELLED` 且统计保留。

### 6.2 前端

- 跨度超过 6 小时时前端拦截并提示。
- 运行中轮询、结束后停止轮询、离开页面清除定时器。
- 运行中显示取消按钮，非运行中不显示。
- 从未提交任务时显示空状态。
