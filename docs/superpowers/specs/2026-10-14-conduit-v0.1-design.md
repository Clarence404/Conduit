# Conduit V0.1 设计（主链路跑通）

- 日期：2026-10-14
- 状态：已评审，待实现
- 范围：本文件定义 Conduit 的版本路线与 V0.1 的详细设计。V0.2 及以后各版本另写 spec。

## 1. 背景与定位

Conduit 是一个个人研究性质的 IoT 平台。定位为「学习研究为主 + 一键演示」：

- 重点是把 IoT 平台的关键机制做透：接入鉴权、消息可靠性、时序建模、协议可扩展。
- 代码清晰可读，核心逻辑有测试覆盖；不追求生产级运维完备度（安全加固、可观测性集中在 V1.0）。
- 任何人 `docker compose --profile demo up -d` 后即可看到平台运行效果。

## 2. 技术栈

| 层 | 选型 |
|---|---|
| 后端 | Java 21、Spring Boot 3、Maven 多模块、MyBatis-Plus、Spring Security、Flyway |
| MQTT Broker | EMQX 5 |
| 消息总线 | Redis Streams（经 `MessageBus` 接口抽象） |
| 时序存储 | InfluxDB 3 Core 3.12（V0.2-A 起；V0.1 为 2.7） |
| 关系存储 | PostgreSQL 16 |
| 缓存 / 状态 | Redis 7（开启 AOF） |
| MQTT 客户端 | HiveMQ MQTT Client（MQTT 5、共享订阅、手动 ACK） |
| 前端 | Vue 3、TypeScript、Vite、Element Plus、Pinia、Vue Router、Axios；ECharts 自 V0.2 引入 |
| 测试 | JUnit 5、AssertJ、Mockito、Testcontainers；前端 Vitest |
| 部署 | Docker Compose；前端由 nginx 容器托管 |

所有镜像固定到具体小版本，不使用 `latest`。

## 3. 版本路线

| 版本 | 主题 | 交付内容 | 完成标志 |
|---|---|---|---|
| V0.1 | 主链路跑通 | 仓库骨架与 Compose；设备注册与凭证；MQTT → connector → Redis Streams → server → InfluxDB；模拟器；前端登录、产品、设备列表、最新值 | 100 台模拟设备在线，前端可见实时值；杀进程不丢数据测试通过 |
| V0.2 | 物模型 + 多租户 | 拆为三个子项目依次实施：A 物模型与编解码（`2026-10-15-conduit-v0.2a-thing-model-design.md`）；B 历史查询与曲线；C 租户隔离（界面）与用户管理 | 两租户两型号数据互不可见，曲线正确 |
| V0.3 | 告警 | 上下线事件记录；阈值告警规则；告警记录与确认；Webhook 通知 | 越限、恢复、离线均能触发并自动恢复 |
| V1.0 | MVP 发布 | 1 万台压测；降采样与保留策略；监控指标；TLS；部署文档；评估 Redis Streams 是否够用 | 1 万台 × 每分钟 1 条，端到端 P99 < 5s，24 小时零丢数 |
| V1.1 | 协议扩展 | HTTP 接入；Modbus TCP（平台侧轮询）；私有 TCP 示例适配器 | 新协议仅新增适配器模块，核心零改动 |
| V1.2 | 设备控制 | 下行命令（回执、超时、重试）；设备影子；远程配置；评估 RabbitMQ 作为下行通道 | 命令全生命周期可查 |
| V2.0 | 开放能力 | 开放 API + AccessKey；数据转发；可配置规则引擎；OTA；评估 Kafka | 第三方可订阅数据，规则无需发版即可修改 |

V0.1 提前埋好的两点：

1. 所有业务表从第一天起带 `tenant_id`，V0.1 只有默认租户，V0.2 补隔离逻辑与界面。
2. 协议适配层从第一天起是 `ProtocolAdapter` 接口 + 实现，V0.1 只有 MQTT 实现。

## 5. 架构

```
设备/模拟器 ──MQTT──▶ EMQX ──HTTP 鉴权回调──▶ conduit-server
                       │
                       │ 共享订阅 + 上下线系统主题
                       ▼
               conduit-connector ──▶ Redis Streams ──▶ conduit-server ──▶ InfluxDB（时序）
                                                         │           ──▶ Redis（最新值、在线状态）
                                                         │           ──▶ PostgreSQL（租户、用户、产品、设备）
                                                         ▼
                                                   Vue 前端（REST）
```

### 5.1 模块职责

| 模块 | 类型 | 职责 | 依赖 |
|---|---|---|---|
| `conduit-common` | 库 | `RawMessage`（productKey、deviceKey、type、原始 payload 字节、receivedAt、可选 eventTime 与附加属性）；`MessageBus` 接口（publish / 消费组订阅 / ack / 认领 / 死信）；`RedisStreamMessageBus` 实现 | Spring Data Redis |
| `conduit-connector` | 应用 | `ProtocolAdapter` 接口；`MqttProtocolAdapter`：订阅 EMQX，解析 topic，组装 `RawMessage` 投递总线。只搬运原始字节，不解析业务内容 | common、HiveMQ MQTT Client |
| `conduit-server` | 应用 | 分包：`auth`（登录/JWT/用户初始化）、`device`（产品、设备、凭证）、`mqttauth`（EMQX 回调）、`pipeline`（消费→解码→校验→入库）、`telemetry`（最新值查询）、`presence`（在线状态） | common、PG、Redis、InfluxDB |
| `conduit-simulator` | 命令行工具 | 通过 REST 创建演示产品与 N 台设备，再按配置周期上报 | common、HiveMQ MQTT Client |

解码放在 server：V0.2 的编解码插件需查物模型、按型号路由，属于业务逻辑。connector 保持纯协议层，新增协议只改 connector。

## 6. 设备侧约定

### 6.1 Topic

| 方向 | Topic | 版本 |
|---|---|---|
| 上行属性 | `conduit/{productKey}/{deviceKey}/up/property` | V0.1 |
| 上行事件 | `conduit/{productKey}/{deviceKey}/up/event` | 预留，V0.3 |
| 下行命令 | `conduit/{productKey}/{deviceKey}/down/command` | 预留，V1.2 |

### 6.2 上行属性 Payload

```json
{
  "id": "可选，消息唯一 ID，仅用于日志追踪",
  "ts": 1760400000000,
  "params": { "Ua": 220.1, "Ia": 5.2, "EPimp": 12345.6 }
}
```

- `ts`：设备采样时间，毫秒级 Unix 时间戳；缺省时取平台接收时间。
- `params`：非空对象；值允许数值、字符串、布尔。
- 在线/离线不由设备上报，由 EMQX 连接事件判定。

### 6.3 连接与鉴权

- `clientId = username = deviceKey`，`password = deviceSecret`。
- EMQX 使用 HTTP 鉴权回调 `POST /internal/mqtt/auth`（见 8.1）。
- ACL 使用 EMQX 文件授权 + `${clientid}` 占位符：设备只能发布 `conduit/+/${clientid}/up/#`，只能订阅 `conduit/+/${clientid}/down/#`。connector 使用独立的内部账号，授权订阅 `conduit/+/+/up/#` 与上下线系统主题。
- V0.1 不启用 TLS（V1.0 统一加）。

## 7. 数据模型

### 7.1 PostgreSQL（Flyway 管理）

主键为 `bigint` 自增，对外只暴露 `product_key` / `device_key`。

| 表 | 字段 |
|---|---|
| `tenant` | id、code（唯一）、name、status、created_at |
| `app_user` | id、tenant_id、username（全局唯一）、password_hash（bcrypt）、role、status、created_at |
| `product` | id、tenant_id、product_key（全局唯一）、name、description、created_at、updated_at |
| `device` | id、tenant_id、product_id、device_key（全局唯一）、name、secret_hash、secret_salt、status（`ENABLED`/`DISABLED`）、created_at、updated_at |

- 启动时若不存在则创建默认租户 `default` 与管理员；管理员用户名、密码来自环境变量。
- `product_key`、`device_key` 由平台生成（16 位小写字母数字）；`deviceSecret` 32 位随机串，只在创建或重置时明文返回一次。
- 密钥存储：`SHA-256(salt + secret)`，比较时用常量时间比较。不用 bcrypt，避免重连风暴时鉴权 CPU 过载。
- 删除产品时若其下仍有设备，返回 409。
- 删除设备时同时清除其 `conduit:latest`、`conduit:presence`、`conduit:auth` 三个 Redis key；InfluxDB 历史数据保留，随保留策略过期。

### 7.2 InfluxDB

- 数据库：`telemetry`，保留 30 天（启动时建库设置）。
- measurement：`property`。
- tag：`tenant_id`、`product_key`、`device_key`。
- field：`params` 中的每个测点，数值统一按 double 写入（避免 int/float 类型冲突），字符串与布尔原样写入（V0.2-A 起按物模型类型写入，见 V0.2-A spec 2.3）。
- 时间：`ts`，毫秒精度。
- 幂等：同设备、同 `ts`、同字段重复写入即覆盖为相同值，重复投递天然无害；V0.1 不按 `id` 去重。

### 7.3 Redis

| Key | 结构 | 用途 |
|---|---|---|
| `conduit:stream:up` | Stream，消费组 `conduit-server`，`MAXLEN ~ 1000000` | 上行数据与上下线事件 |
| `conduit:stream:dead` | Stream，`MAXLEN ~ 100000` | 死信：原始消息、原因、时间 |
| `conduit:latest:{deviceKey}` | Hash：测点 → `{"v":…, "ts":…}` | 最新值；Lua 脚本逐测点比较 ts，只有更新的才覆盖 |
| `conduit:presence:{deviceKey}` | Hash：online、since、clientIp | 在线状态；事件时间更新的才生效 |
| `conduit:auth:{deviceKey}` | String，TTL 5 分钟 | 鉴权凭证缓存；禁用、重置密钥、删除时主动删除 |

## 8. 数据流

### 8.1 设备连接鉴权

1. 设备 CONNECT。
2. EMQX 调用 `POST /internal/mqtt/auth`，携带 clientid、username、password 及请求头 `X-Conduit-Internal-Token`。
3. server 校验内部 token；查 `conduit:auth:{deviceKey}`，未命中查 PG 并回填缓存。
4. 校验：设备存在且 `ENABLED`、clientid == username == deviceKey、密钥哈希匹配。
5. 返回 `{"result":"allow"}` 或 `{"result":"deny"}`。

### 8.2 上行数据（至少一次投递）

1. 设备以 QoS1 发布到 `.../up/property`。
2. connector 以持久会话共享订阅 `$share/conduit/conduit/+/+/up/#`，手动 ACK。
3. connector 解析 topic 得到 productKey、deviceKey、消息类型，组装 `RawMessage`，`XADD` 到 `conduit:stream:up`；**XADD 成功后才回 PUBACK**。
4. server 以消费组读取，每批最多 100 条，阻塞 1 秒。
5. 逐条：解码 JSON → 校验（见 9.1）→ 转换为 Influx point。
6. 批量写 InfluxDB → Lua 更新最新值 → `XACK`。

每一跳都是下游确认后才确认上游：任一环节崩溃，消息留在 EMQX 会话或 Stream PEL 中，不丢失，最多重复，由 InfluxDB 覆盖语义吸收。

### 8.3 上下线

1. connector 共享订阅 EMQX 系统主题 `$SYS/brokers/+/clients/+/connected` 与 `.../disconnected`。
2. 组装 `RawMessage(type=PRESENCE)`，附带事件时间、clientIp，投入同一条 Stream。
3. server 更新 `conduit:presence:{deviceKey}`，只有事件时间晚于当前记录才生效，防止快速断连重连时旧事件覆盖新状态。
4. connector 自身的内部账号连接事件忽略。

## 9. 错误处理

原则：可恢复的错误重试，不可恢复的错误进死信；任何消息要么入库，要么进死信。

### 9.1 消息本身有问题（进死信，原消息 XACK）

| 情况 | 死信原因码 |
|---|---|
| JSON 解析失败 | `MALFORMED_JSON` |
| `params` 缺失、为空或非对象 | `INVALID_PARAMS` |
| 设备不存在 | `UNKNOWN_DEVICE` |
| 设备已禁用 | `DEVICE_DISABLED` |
| productKey 与设备不匹配 | `PRODUCT_MISMATCH` |
| `ts` 超出 `[now − 30 天, now + 5 分钟]` | `TS_OUT_OF_RANGE` |
| InfluxDB 字段类型冲突 | `FIELD_TYPE_CONFLICT` |
| V0.1 尚未支持的消息类型（如 `up/event`） | `UNSUPPORTED_TYPE` |
| 意外处理异常（只影响该条消息） | `PROCESSING_ERROR` |

- 字段类型冲突：整批写入返回 4xx 时拆为逐条写入，只将失败条目送入死信。
- 每个原因码有独立计数（Micrometer 指标）。
- V0.1 查看死信依赖 `redis-cli` 与日志。

### 9.2 下游暂时不可用（重试）

- InfluxDB / Redis 写入失败（网络错误、5xx）：不 XACK，在原地指数退避重试（1s 起，上限 30s），不重新读取，因此不消耗投递次数。
- 实例崩溃遗留的 PEL 消息：定时通过 Lua 脚本执行 `XPENDING ... IDLE` 筛出空闲超过 60 秒的消息，再 `XCLAIM` 认领；投递次数超过 5 次进死信（原因码 `MAX_DELIVERY_EXCEEDED`）。

### 9.3 接入侧

- connector 与 EMQX 断线：客户端自动重连，持久会话保证消息不丢。
- connector 写 Redis 失败：不回 PUBACK，消息留在 EMQX 会话等待重投。
- 已知限制：EMQX 会话队列有上限（`max_mqueue_len`），Redis 长时间宕机会导致溢出丢失；在部署文档中注明，V1.0 压测时量化。
- 已知限制：`conduit:stream:up` 使用 `MAXLEN ~` 近似裁剪，服务端长时间宕机时，超出上限（约 100 万条，高负载下约几十分钟）的未消费或仍在 pending 的条目会被静默裁掉，XCLAIM 取不回，与“每条消息要么入库要么进死信”不完全一致；V1.0 压测时量化。
- 已知限制：V0.1 假定只部署单个 conduit-server 实例；多实例时，原地重试耗时超过 claim-min-idle 会让另一实例认领同一批消息（重复处理，并消耗投递次数）。
- 已知限制：禁用设备不会断开其在线 MQTT 会话，其后续消息会成为 DEVICE_DISABLED 死信，直到设备重连；V0.2 可通过 EMQX API 踢掉会话。
- 运维约束：connector 的 clientId 必须按实例稳定（下线实例的持久会话在过期前仍占用 `$share` 组成员资格，会分走消息）；XPENDING 的 IDLE 过滤需要 Redis ≥ 6.2。
- 鉴权回调失败：EMQX 拒绝连接，设备自动重连，不丢数据。Redis 缓存不可用时降级直查 PG。

### 9.4 接口层

统一使用 RFC 9457 `ProblemDetail`：400 参数错误、401 未认证、403 无权限、404 不存在、409 冲突。

## 10. REST 接口

前缀 `/api/v1`；租户隔离由 MyBatis-Plus `TenantLineInnerInterceptor` 从 JWT 的 `tenant_id` 自动拼接条件。

| 分组 | 接口 | 说明 |
|---|---|---|
| 认证 | `POST /auth/login` | 返回 access token；refresh token 写入 HttpOnly Cookie |
| | `POST /auth/refresh` | 用 Cookie 中的 refresh token 换新 access token |
| | `POST /auth/logout` | 清除 refresh token |
| 产品 | `GET /products`、`POST /products` | 列表、新建 |
| | `GET/PUT/DELETE /products/{productKey}` | 详情、修改、删除（有设备时 409） |
| 设备 | `GET /devices?productKey=&keyword=&page=&size=` | 分页查 PG，当前页在线状态与最后上报时间用 Redis pipeline 补齐 |
| | `POST /devices` | 新建，响应中唯一一次返回 deviceSecret |
| | `GET/PUT/DELETE /devices/{deviceKey}` | 详情、改名称/状态、删除 |
| | `POST /devices/{deviceKey}/reset-secret` | 重置密钥，返回一次新密钥 |
| 数据 | `GET /devices/{deviceKey}/latest` | 最新值 |
| 内部 | `POST /internal/mqtt/auth` | 仅 EMQX 调用，校验内部 token，不走 JWT |

- access token 有效期 15 分钟，refresh token 7 天。
- 「按在线状态筛选」与历史查询不在 V0.1 范围。

## 11. 前端

| 路由 | 内容 |
|---|---|
| `/login` | 登录 |
| `/products` | 产品列表、新建、删除 |
| `/devices` | 设备列表：设备 Key、名称、产品、在线状态、最后上报时间；操作：详情、启用/禁用、重置密钥、删除；新建后弹窗一次性显示密钥，带复制按钮 |
| `/devices/:key` | 基本信息；连接参数卡片（地址、端口、clientId、username、topic 与 payload 示例）；最新值表格每 5 秒轮询 |

- access token 仅存于 Pinia 内存；Axios 遇 401 先刷新一次再重试，刷新失败跳转登录。
- 开发时 Vite 代理 `/api` 到 `localhost:8080`；演示时由 nginx 托管静态文件并反向代理。

## 13. 一键演示

```
deploy/
├── docker-compose.yml   emqx / redis(AOF) / postgres / influxdb /
│                        conduit-server / conduit-connector / conduit-web(nginx)
│                        simulator 位于 profile: demo
├── .env.example         管理员密码、内部 token、connector 账号、InfluxDB token 均为占位符
└── emqx/                鉴权回调与 ACL 配置
```

流程：

1. `cp deploy/.env.example deploy/.env`，修改其中的口令与 token。
2. `docker compose -f deploy/docker-compose.yml --profile demo up -d --build`。
3. 模拟器以管理员身份调用 REST 创建演示产品与 100 台设备，拿到密钥后连接 MQTT，每 10 秒上报一次三相电压、电流、电能。
4. 浏览器打开 `http://<docker-host>:8090`（`WEB_PORT`，Docker 在本机时为 `localhost`），登录后可见 100 台设备在线、最新值刷新。

可配置端口：`WEB_PORT`(8090)、`API_PORT`(8091)、`MQTT_PORT`(1883)、`EMQX_DASHBOARD_PORT`(18083)、`INFLUX_PORT`(8096)；绑定地址 `BIND_ADDR` 默认 `127.0.0.1`，远程 Docker 宿主机需设为 `0.0.0.0`。

真实凭证不入库，`.env` 加入 `.gitignore`。

## 14. V0.1 完成标准
